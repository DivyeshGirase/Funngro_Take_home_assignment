# Wallet balance notifications

I would first trace a wallet change from the API or job to the database and read the tests, ledger entries and transaction boundaries. I'd search for writes to the wallet model, collection and balance fields, including bulk writes, then check webhooks, scheduled jobs, admin tools and scripts with the team. I'd trace deposits, withdrawal reservations, refunds, rewards and admin adjustments. Here the withdrawal handler debits the wallet and the payout worker can refund it. A hook only in the withdrawal route would miss the refund and other credits.

I'd write a `wallet_balance_changed` outbox event alongside each wallet update and ledger entry in the same MongoDB transaction. A rollback would remove the event as well. I'd reuse the payout outbox's leasing and retry approach, with a separate event type and a notification consumer that claims only its own events. The consumer can wake on committed inserts and poll as a fallback so queued work is picked up after restarts. It sends as soon as it claims the event, outside the wallet transaction.

I'd derive a unique event ID from the ledger or mutation ID and pass that ID to the provider as its idempotency key where supported. A timeout or crash after the provider accepts a send can leave delivery uncertain. The worker retries with backoff and the same ID, and alerts on repeated failures. Without provider deduplication, delivery can still repeat. I'd increment a version in the wallet update and record it in the event. The app can ignore older versions and fetch the latest authorised balance when opened. I'd keep push messages generic and leave balances, bank details and tokens out of push payloads and logs.

Sending before commit can alert users to a debit that was rolled back. Sending only after commit without a durable event can lose the alert if the process crashes. Calling the provider in the request can slow withdrawals or cause financial operations to fail when the provider is down. Concurrent changes and retries can send duplicates or show an older balance as current. An overly detailed message can expose financial information on a lock screen.

I'd test each balance-changing path, rollback, a crash after sending, provider timeouts and two rapid changes arriving out of order. I'd start with a small group and monitor the time from commit to delivery, retries and stuck events before expanding.
